# 목표 설정 재구성 — 지역 드롭다운과 목표 가격 설계안

- 작성일: 2026-07-31
- 대상 저장소: `housing-finance-web`
- 선행 문서: `2026-07-30-desired-home-map-design.md`(희망 주택 패널 골격 — 본 문서가 §3.2·§4.4를 대체)

---

## 1. 배경과 범위

`step 1. 정보 입력`의 `목표 설정`을 재구성한다.

- `목표 금액 (원)` 입력을 `목표 설정` 기본 행에서 뺀다.
- `희망 주택` 패널의 토글 버튼 두 개(`지역`·`목표 가격`)를 **실제 입력 필드**로 바꾼다 —
  `지역`은 서울 25개 구 드롭다운, `목표 가격`은 금액 입력.
- 두 필드를 지도 박스 **바깥**에, `목표 시점`·`위험 성향`과 같은 형식·크기로 그 아래에 놓는다.
- 두 필드를 **필수**로 만들고, 채워지기 전에는 `다음` 버튼을 누를 수 없게 한다.

### 1.1 이 문서가 다루지 않는 것 (별도 사이클)

사용자 요청은 세 덩어리이며 이 문서는 **A만** 다룬다.

| 덩어리 | 내용 | 상태 |
|---|---|---|
| **A. 폼·레이아웃 재구성** | 이 문서 | 이번 사이클 |
| **B. DB 접속 인프라** | SSH 터널 + Postgres 연결, 접속 정보 `.env` | 다음 사이클 |
| **C. 부동산 데이터 API** | core에 엔드포인트 추가 → 웹이 호출 | 다음 사이클 |

A는 B·C 없이 완결된다. 서울 25개 구는 고정 목록이므로 드롭다운에 DB가 필요 없다.

### 1.2 대상 DB에 대한 확인된 사실 (B·C 설계 시 전제)

첨부된 `db_schema_realestate.md` 기준으로, 이 DB는 **판매 중인 매물 목록을 담고 있지 않다.**
`apt_trades`는 2025-07-01~2026-07-22 실거래 **체결 이력**이고, 동·호수 컬럼이 없어 개별 물건을
식별할 수 없다(문서 "참고 1"이 명시). 따라서 B·C에서 얻을 수 있는 것은
`fn_price_reference(법정동코드, 평형)` → 중위가격·1·3분위수이며, `목표 가격`은
"매물을 골라 그 가격을 쓴다"가 아니라 **"지역·평형 시세 중위값을 기본값으로 제안하고
사용자가 수정한다"** 형태가 된다. 이번 사이클의 `목표 가격`은 그 자리를 미리 만들어 두는 것이다.

## 2. 레이아웃

```
목표 설정                                    [ 희망 주택 ]
현재 페르소나의 목표 금액은 …

┌────────────────────────┬────────────────────────┐
│ 목표 시점 (YYYY-MM)     │ 위험 성향               │   md:grid-cols-2
│ [2028-07           ]   │ [안정형             ▾] │
└────────────────────────┴────────────────────────┘

  ↓ [희망 주택]을 누르면 아래가 나타난다

┌────────────────────────┬────────────────────────┐
│ 지역                    │ 목표 가격 (원)          │   같은 md:grid-cols-2
│ [강남구             ▾] │ [50000000          ]   │   같은 FieldRow
└────────────────────────┴────────────────────────┘
┌──────────────────────────────────────────────────┐
│                  대한민국 지도                     │  지도만 테두리 유지
└──────────────────────────────────────────────────┘
```

`GoalFields`의 그리드를 `md:grid-cols-3`에서 **`md:grid-cols-2`로 바꾸고**, 희망 주택 영역도
같은 `md:grid-cols-2`를 쓴다. 두 행의 열 너비가 정확히 일치한다.

기존 `DesiredHomePanel`의 감싸개(`rounded-xl border border-line bg-surface/60 p-4`)를
**제거한다.** 두 필드가 다른 `FieldRow`처럼 맨바닥에 놓여야 "박스 바깥"이 된다. 테두리를 갖는
것은 `KakaoMap`의 `<section>` 하나뿐이다.

토글 버튼 두 개는 **사라진다.** 그 라벨(`지역`·`목표 가격`)이 그대로 필드 라벨이 된다.

## 3. 필드

### 3.1 target_price — 이름 유지, 위치·라벨만 변경

| 항목 | 이전 | 이후 |
|---|---|---|
| 스키마 키 | `target_price` | `target_price` (변경 없음) |
| 라벨 | `목표 금액 (원)` | `목표 가격 (원)` |
| 위치 | `GoalFields` 1번 칸 | 희망 주택 영역 2번 칸 |
| 입력 | `<Input type="number">` + `formatKoreanUnit` 힌트 | 동일 |

키를 유지하므로 `persona.ts` 계약 2곳, 픽스처 60여 곳, `persona-grid.tsx`, 대시보드는
**건드리지 않는다.**

### 3.2 target_region — 신규 폼 필드

키는 이미 페르소나 계약에 있다(`personaProfileSchema.goal.target_region`, 5자리 시군구 코드
문자열). 계약 변경 없이 폼 스키마에만 추가한다.

```ts
target_region: z.string().min(1, "지역을 선택하세요"),
```

`<option>` 요소는 27개이고, 그중 **선택 가능한 것은 26개**다.

| 순서 | value | 라벨 | 의미 |
|---|---|---|---|
| 1 | `""` | `지역을 선택하세요` (`disabled`) | 미선택. 검증 실패. 값이 `""`인 동안 무엇이 보일지 정하기 위해 필요하다 |
| 2 | `ALL` | `전체 (서울 25개 구)` | 아직 지역을 좁히지 못한 사용자. B·C에서 25개 구 전역 조회로 해석 |
| 3~27 | `11110` … `11740` | `종로구` … `강동구` | 개별 자치구 |

빈 값 자리표시 옵션이 **반드시 있어야 한다.** `<select>`는 현재 값이 어떤 `<option>`과도
맞지 않으면 첫 옵션을 그려 버리므로, 자리표시가 없으면 값이 `""`인데 화면에는
`전체 (서울 25개 구)`가 선택된 것처럼 보인다. 사용자는 이미 골랐다고 믿는데 `다음`은
잠겨 있는 상태가 된다. `disabled`를 붙이는 이유는 한 번 고른 뒤 미선택으로 되돌아갈
경로를 막기 위해서다.

`ALL`을 별도 센티널로 두는 이유: 빈 문자열은 "아직 안 골랐다", `ALL`은 "전체로 골랐다"로
의미가 다르다. 하나로 합치면 필수 입력 검증이 성립하지 않는다.

문자열은 두 군데에서 다르게 쓰며, 각각 고정값이다.

| 쓰임 | `ALL` | 개별 구 |
|---|---|---|
| 드롭다운 옵션 (`desired-home-panel.tsx`) | `전체 (서울 25개 구)` | `강남구` |
| 입력 확인 요약 (`step-review.tsx`, `seoulDistrictLabel()`) | `서울 전체` | `강남구` |

`seoulDistrictLabel(code)`는 요약용이다 — `ALL` → `서울 전체`, 25개 구 코드 → 구 이름,
그 외(빈 문자열 포함) → 받은 코드를 그대로 반환한다(`codes.ts`의 `lookup`과 같은 관용).
드롭다운의 `전체 (서울 25개 구)`는 옵션 목록에만 쓰는 별도 문자열이다.

### 3.3 프리필 규칙

`toFormValues(profile)`가 `profile.goal.target_region`을 넣되, **서울 25개 구 코드가 아니면
빈 문자열로 시작한다.**

**픽스처 데이터는 이 사이클에서 이미 정리했다.** 원래 20명 중 11명이 서울 밖
(`26440` 부산 강서 2명, `27200` 대구 남구 2명, `29170` 광주 서구 3명, `30200` 대전 유성 4명)
이었고, 이를 서울 25개 구에서 무작위로 뽑은 값으로 교체했다. 이제 20명 전원이 서울이다.

| 페르소나 | 이전 | 이후 |
|---|---|---|
| `persona_e_college_student_basic` | 30200 | `11650` 서초구 |
| `persona_g_college_student_03_basic` | 30200 | `11260` 중랑구 |
| `persona_i_college_student_05_basic` | 29170 | `11560` 영등포구 |
| `persona_j_college_student_06_basic` | 30200 | `11440` 마포구 |
| `persona_r_college_student_14_poor` | 29170 | `11350` 노원구 |
| `persona_s_college_student_15_poor` | 27200 | `11320` 도봉구 |
| `persona_t_college_student_16_poor` | 26440 | `11230` 동대문구 |
| `persona_u_college_student_17_poor` | 29170 | `11500` 강서구 |
| `persona_v_college_student_18_poor` | 27200 | `11200` 성동구 |
| `persona_w_college_student_19_poor` | 26440 | `11710` 송파구 |
| `persona_x_college_student_20_poor` | 30200 | `11620` 관악구 |

픽스처는 3단계로 생성되므로 세 곳을 모두 고쳤다 —
`housing-finance-core`의 `generate_all.py`(생성기, 별도 저장소) →
같은 저장소의 `mydata/<persona>/user_profile.json` →
`npm run build:fixtures`로 재생성한 웹의 `src/mocks/fixtures/<persona>/profile.json`.
생성기를 고치지 않으면 다음 재생성 때 되돌아간다.

`housing-finance-core`의 `persona_b_newlywed_jeonse`는 `41135`(경기 성남 분당)로 남아 있다.
대학생 20명 밖이고 웹 픽스처에 포함되지 않아 범위에서 제외했다.

빈 문자열 폴백은 **방어 코드로 남긴다.** 현재 어떤 픽스처도 이 경로를 타지 않지만,
B·C에서 서울 밖 데이터가 들어올 여지가 있고, 검증되지 않은 코드를 드롭다운 값으로
그대로 흘리는 것보다 미선택으로 떨어뜨리는 편이 안전하다.

## 4. 필수 입력과 다음 버튼

### 4.1 동작

`step 1`의 `다음` 버튼은 `target_region`이나 `target_price`가 비어 있으면 **비활성화**된다.

비활성화된 동안 버튼 옆에 사유를 표시한다:

> 희망 주택의 지역과 목표 가격을 입력해주세요.

문구를 다는 이유는 막다른 길을 막기 위해서다. 두 필드는 접힌 패널 안에 있으므로, 문구가
없으면 화면 어디에도 원인이 보이지 않는 채 버튼만 죽어 있다. 문구는 `희망 주택`이라는
단어를 포함해 어디를 열어야 하는지 가리킨다.

**실제로 이 게이트가 걸리는 경로는 `목표 가격` 하나다.** §3.3의 픽스처 정리로 지역은 항상
프리필되고, 자리표시 옵션이 `disabled`라 사용자가 지역을 미선택으로 되돌릴 수단이 없다.
반면 `목표 가격`은 숫자 입력이라 비울 수 있다. `target_region`의 `.min(1)` 검증과 빈 값
판정은 방어 코드로 남지만, 현재 UI에서 발화하지 않는다.

### 4.2 판정 방식

`InputWizard`가 `form.watch(["target_region", "target_price"])`로 두 값만 구독하고,
어느 하나라도 비어 있으면 비활성화한다. 빈 값 판정은 `""`, `undefined`, `null` 세 가지다 —
`<input type="number">`는 비우면 `""`를 돌려주고, `defaultValues`는 `number`를 넣으므로
두 타입을 모두 받아야 한다.

`formState.isValid`(`mode: "onChange"`)를 쓰지 않는 이유: 그 방식은 나이·월소득 등 **모든**
필드로 비활성화 조건이 번져 기존 동작(누르면 에러 표시)이 통째로 바뀐다. 요청은 두 필드에
한정되므로 두 필드만 구독한다.

### 4.3 남는 경계 사례

`target_price`를 지운 뒤 패널을 닫으면 값은 유지되고(react-hook-form은 언마운트 시 값을
버리지 않는다) 버튼은 비활성 상태로 남는다. 4.1의 문구가 이 상태에서도 그대로 보이므로
사용자는 `희망 주택`을 다시 열어 고칠 수 있다.

## 6. 지도

지도는 그대로 둔다. **지역 선택이 지도를 움직이지는 않는다** — 이번 범위가 아니다.

주의: `KakaoMap`은 `center`/`level` prop이 바뀌면 기존 인스턴스에 `setCenter`를 호출하지 않고
같은 컨테이너에 새 `Map`을 만든다(선행 사이클 리뷰의 알려진 항목). 나중에 "구를 고르면 지도가
그 구로 이동" 기능을 붙일 때는 이 effect를 `mapRef` + `setCenter`/`setLevel`로 먼저 고쳐야 한다.

### 7.3 기존 위저드 테스트에 미치는 파급

§3.3에서 픽스처를 정리해 20명 전원이 서울 구를 갖게 되었으므로, **지역이 비어 시작하는
페르소나는 없다.** `다음` 버튼은 처음부터 열려 있고, 그 버튼을 누르는 기존 테스트
(단계 이동 4개, 검증 실패 3개)는 **손댈 필요가 없다.**

정리 전이었다면 기본 샘플인 `persona_e`(대전 유성)가 빈 지역으로 시작해 `다음`이 잠기고,
"나이를 비우면 넘어가지 않는다" 같은 검증 테스트까지 버튼을 못 눌러 함께 막혔을 것이다.
데이터를 고친 덕분에 이 파급이 통째로 사라졌다.

### 7.4 고쳐야 하는 기존 테스트

`input-wizard.test.tsx`의 `목표 금액 (원)` 참조 3곳(프리필 확인, 값 변경 후 `edited=1` 확인)을
새 라벨·위치에 맞춘다. 값을 바꾸려면 먼저 `희망 주택`을 열어야 한다.

`step-input.test.tsx`의 "패널을 열어도 목표 금액 입력은 그대로다"는 `목표 금액 (원)`이
사라졌으므로 대상 필드를 `목표 시점`으로 바꾼다.

## 9. 다음 사이클 입력 (B·C)

- SSH 터널을 누가 여는가 — FastAPI core 프로세스가 직접 여는지, 개발자가 `ssh -L`로 여는지
- 부동산 DB가 core의 기존 `database_url`(compose의 `housing` DB)과 별개 연결인지
- `fn_price_reference` 결과를 어느 시점에 `target_price` 기본값으로 채울지 (지역 선택 직후 vs 명시적 버튼)
- `평형(area_band)` 입력이 필요한데 현재 폼에 없다 — 어디에 둘지
- `ALL` 선택 시 시세를 어떻게 낼지 (25개 구 통합 중위값 vs 시세 제안 생략)
- `toFormValues`는 동기 함수인데 `isSeoulDistrict`에 의존한다. 구 목록이 API에서 오면
  동기 프리필 검증이 불가능해진다 — `SEOUL_DISTRICTS`를 정적 시드로 남기고 API는 갱신만
  하게 하거나, "모르는 코드는 미선택으로" 판단을 `toFormValues` 밖 effect로 옮겨야 한다.

## 1. 왜 바꾸는가

직전 사이클은 자치구를 고르면 `apt_price_stats`의 5개 평형대 중위가를 보여줬다.
사용자 요청은 **거래된 매물을 전부** 보는 것이고, 이유가 타당하다 —
**같은 아파트·같은 면적이라도 층마다 거래가격이 다르다.**

집계로는 그 차이를 보여줄 수 없다. 중위값 하나로 뭉개면 층과 가격의 짝이 끊긴다.

### 1.1 중복을 합치지 않는다

초안에서는 "같은 아파트는 한 줄로 합치고 가격은 중위값"을 검토했다. 실측 결과
합치면 층을 표시할 수 없다.

| 중복 제거 단위 | 행 수 | 층 표시 |
|---|---|---|
| 아파트 | 5,953 | 불가 (면적도 뭉개짐) |
| 아파트+정확면적 | 15,054 | **61%가 층 여러 개** (평균 3.64종, 최대 30종) |
| **합치지 않음** | **75,240** | **정확** |

그래서 합치지 않는다. 한 행 = 한 건의 실거래이며, 층과 가격이 같은 거래에서 온다.

### 1.2 계약일을 컬럼에 넣는다

요청 컬럼은 아파트명·법정동·도로명·건축년도·전용면적·층 여섯이지만
**계약일을 하나 더 넣는다.**

같은 `(아파트, 면적, 층)` 조합에 거래가 2건 이상인 경우가 **13,044조합 33,515건**
있다. 계약일이 없으면 화면에 완전히 똑같아 보이는 줄이 가격만 다르게 여러 번
나오고, 사용자는 그것이 오류인지 서로 다른 거래인지 알 방법이 없다.
거래별로 보여주기로 한 이상 계약일이 그 행을 구별하는 유일한 값이다.

## 2. 데이터

`v_valid_trades`를 읽는다. 해제 거래와 토지임대부를 이미 제외한 뷰이며,
스키마 문서 §7이 "백엔드는 `apt_trades`가 아니라 이 뷰를 읽는다"고 못박고 있다.

해제 거래 3,037건 중 2,355건이 정상 거래와 쌍으로 존재하므로, 뷰를 우회하면
같은 거래가 두 번 보이고 해제된 신고가가 최고가로 표시된다.

**규모** (총 75,240건, 5개씩):

| 구 | 거래 | 페이지 |
|---|---|---|
| 노원구 | 7,483 | 1,497 |
| 강서구 | 4,939 | 988 |
| 종로구 | 665 | 133 |

**NULL**: 표시 컬럼 중 `road_nm`만 159건 비어 있다. 나머지는 전부 채워져 있다.

## 3. API

```
GET /api/v1/properties/trades
      ?sgg_code=11680&sort=area_asc&page=1&page_size=5
```

`/price-reference`는 **삭제한다.** 쓰는 곳이 없어지고, 남겨두면 두 엔드포인트가
같은 질문에 다른 답을 하게 된다.

### 3.1 계약

```python
class TradeSort(StrEnum):
    AREA_ASC   = "area_asc"     # 좁은 면적 순 (기본)
    AREA_DESC  = "area_desc"    # 넓은 면적 순
    PRICE_ASC  = "price_asc"    # 가격 낮은 순
    PRICE_DESC = "price_desc"   # 가격 높은 순

class RegionTrade(BaseModel):
    trade_id: int
    apt_name: str
    umd_name: str                 # 법정동
    road_name: str | None         # 159건 NULL
    build_year: int
    exclusive_area_m2: Decimal
    floor: int                    # 음수 허용 — 지하 거래 10건
    contract_date: date
    deal_amount_won: int

class RegionTradePage(BaseModel):
    schema_version: Literal["1.0.0"] = "1.0.0"
    sgg_code: str
    sgg_name: str
    sort: TradeSort
    page: int
    page_size: int
    total_count: int
    total_pages: int
    trades: tuple[RegionTrade, ...]
```

`floor`에 `ge=0`을 걸지 않는다. 지하 거래(`-1`)가 10건 존재한다.

### 3.2 정렬은 반드시 유일한 보조키를 갖는다

```sql
ORDER BY exclu_use_ar ASC, id     -- id가 없으면 안 된다
```

면적·가격은 중복이 흔하다. 동점 처리가 비결정적이면 **PostgreSQL이 페이지마다
다른 순서를 줄 수 있고, 그러면 어떤 거래는 두 페이지에 나오고 어떤 거래는
어느 페이지에도 안 나온다.** `id`를 마지막 정렬키로 붙여 전순서를 만든다.

정렬 문자열은 열거형 → 고정 SQL 조각 매핑으로만 만든다. 사용자 입력을
`ORDER BY`에 잇지 않는다.

### 3.3 상태

| 상황 | 응답 |
|---|---|
| 코드 형식 오류 / `page` < 1 / `page_size` 범위 밖 | 422 |
| 공급자 `disabled`, 연결 실패 | 503 |
| `sgg_codes`에 없는 코드 | 404 |
| 범위를 넘은 `page` | 200, `trades: []` |

마지막 항목을 404로 하지 않는 이유: 정렬을 바꾸면 총 페이지 수가 그대로여도
사용자가 보던 페이지가 유효할 수 있고, 빈 페이지는 오류가 아니라 목록의 끝이다.

`page_size`는 1~50으로 제한한다. 화면은 5를 쓰지만 값을 코드에 박지 않는다.

## 4. 화면

```
지역 [강남구 ▾]              목표 가격 (원) [            ]

강남구 실거래 3,912건                      [좁은 면적 순 ▾]
┌──────────────────────────────────────────────────────┐
│ 개포주공1단지   개포동 · 언주로 · 1982년              │
│ 34.44㎡ · 5층 · 2026-03-14           22억 5,000만원 │
├──────────────────────────────────────────────────────┤
│ 래미안블레스티지 개포동 · 삼성로 · 2019년             │
│ 59.92㎡ · 11층 · 2026-05-02          28억           │
└──────────────────────────────────────────────────────┘
                  ‹ 1 2 3 … 783 ›
```

- 행을 누르면 그 거래의 금액이 `목표 가격`에 들어간다(기존 동작 유지).
- 정렬 드롭다운의 초기값은 `좁은 면적 순`이며, 이것이 요청하신 기본 정렬(면적 오름차순)이다.
- 정렬을 바꾸면 **1페이지로 돌아간다.** 783페이지에서 정렬만 바꾸면 사용자가
  맥락을 잃은 채 목록 한가운데에 떨어진다.
- 페이지 번호는 1,497개를 다 늘어놓을 수 없으므로 `‹ 1 … 748 749 750 … 1497 ›`로 줄인다.
- `road_name`이 없으면 그 자리를 비운다(`법정동 · 1982년`).

**표는 여전히 제안일 뿐이다.** 조회가 실패해도 `목표 가격` 직접 입력과 `다음`
버튼은 그대로 동작한다.

### 4.1 상태

| 상태 | 조건 |
|---|---|
| 미선택 | `target_region === ""` |
| 전체 | `ALL` — 25개 구 전체 조회는 하지 않는다 |
| 로딩 / 정상 / 빈 목록 / 오류 | 기존과 동일 |

`ALL`을 조회하지 않는 이유가 바뀌었다. 이전에는 "서울 전체 grain이 없어서"였고,
지금은 **75,240건 15,048페이지**가 되어 목록으로서 의미가 없기 때문이다.

`AreaBand`는 사라진다. 평형 구간을 더는 화면에 쓰지 않는다.

**설정 키 `REGION_PRICE_PROVIDER`는 이름을 유지한다.** 뜻은 "지역 부동산 데이터
공급자"로 그대로 통하고, 바꾸면 이미 `.env`에 값을 넣어 둔 개발자 환경이
조용히 기본값 `disabled`로 떨어져 503이 난다. 이름을 고쳐 얻는 것보다 잃는 것이 크다.
